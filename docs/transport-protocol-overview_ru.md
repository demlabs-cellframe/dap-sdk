# DAP SDK — Обзор транспорта и протокола

> **Version:** 1.0 | **Date:** 2026-07-20 | **Scope:** DAP SDK Transport & Protocol

## 1. Многоуровневая архитектура

Полная схема сетевого стека DAP SDK от аппаратного уровня до приложений:

```
┌──────────────────────────────────────────────────────────────────┐
│ L4: Каналы и приложения                                          │
│     dap_stream_ch_t — VPN-сервис, GlobalDB, Chain, кастомные     │
├──────────────────────────────────────────────────────────────────┤
│ L3: DAP Stream Protocol                                          │
│     dap_stream_t, dap_stream_pkt_t, фрагментация, сессии         │
├──────────────────────────────────────────────────────────────────┤
│ L2: Transport Abstraction                                        │
│     dap_net_trans_t, vtable (17 операций), обфускационный хук    │
├──────────────────────────────────────────────────────────────────┤
│ L1: Конкретные транспорты                                        │
│     TLS mimicry | UDP basic/reliable | HTTP | DNS tunnel | WS    │
├──────────────────────────────────────────────────────────────────┤
│ L0: IO Layer                                                     │
│     dap_events_socket_t, dap_worker_t, epoll/kqueue/IOCP         │
└──────────────────────────────────────────────────────────────────┘
```

### L0: IO Layer

Фундамент стека. Предоставляет кроссплатформенный event-driven ввод-вывод на базе пула воркер-потоков. Каждый сокет привязан к одному воркеру — никакого contention между потоками. Платформенный механизм выбирается автоматически: epoll (Linux), kqueue (macOS/BSD), IOCP (Windows), poll (fallback).

**Подробнее:** [transport/01-io-layer](transport/01-io-layer_ru.md)

### L1: Concrete Transports

Шесть конкретных реализаций транспорта, каждая реализует `dap_net_trans_ops_t` vtable:

| Транспорт | Назначение |
|-----------|-----------|
| TLS Mimicry | Обход DPI через имитацию TLS 1.3 handshake |
| UDP Basic | Базовый UDP без гарантий доставки |
| UDP Reliable | UDP с ARQ для гарантии доставки |
| HTTP | Туннелирование через HTTP-соединения |
| DNS Tunnel | Туннелирование через DNS-запросы |
| WebSocket | Транспорт поверх WebSocket |

**Подробнее:** [transport/03-transports](transport/03-transports_ru.md)

### L2: Transport Abstraction

Единый интерфейс `dap_net_trans_t` с vtable из 17 операций. DAP Stream Protocol не знает, какой транспорт используется — он работает только с абстракцией. Каждый транспорт декларирует capabilities через битовую маску `DAP_NET_TRANS_CAP_*`. Содержит хук обфускации для обработки пакетов до отправки в сеть.

**Подробнее:** [transport/02-transport-abstraction](transport/02-transport-abstraction_ru.md)

### L3: DAP Stream Protocol

Бинарный потоковый протокол с фрагментацией, мультиплексированием каналов, шифрованием и keepalive. Каждый поток (`dap_stream_t`) связан с сессией и может содержать до 256 каналов. Пакеты разбиваются на фрагменты, учитывающие MTU транспорта.

**Подробнее:** [protocol/01-stream-protocol](protocol/01-stream-protocol_ru.md)

### L4: Channels & Applications

Каналы (`dap_stream_ch_t`) — логические потоки внутри одного DAP Stream. Каждый канал имеет тип и свой обработчик. Примеры: VPN-сервис, GlobalDB-синхронизация, блокчейн-цепочка.

## 2. Как всё работает вместе

Сквозной поток данных от подключения клиента до передачи данных:

```
Клиент                                          Сервер
  │                                                │
  │  1. Выбор транспорта (напр. TLS_DIRECT)        │
  │                                                │
  │  2. IO layer устанавливает TCP-соединение       │
  │  ─────────────────────────────────────────────→ │
  │                                                │
  │  3. Transport создаёт esocket и stream          │
  │                                                │
  │  4. DSHP handshake: обмен ключами              │
  │     (post-quantum KEM: Kyber / Falcon)          │
  │  ←───────────────────────────────────────────→  │
  │                                                │
  │  5. Создание сессии со списком каналов          │
  │                                                │
  │  6. Передача данных:                            │
  │     app → channel_pkt → stream_pkt              │
  │         → fragment → transport → network        │
  │  ─────────────────────────────────────────────→ │
  │                                                │
  │  7. Приём данных:                               │
  │     network → transport → defragment            │
  │         → decrypt → channel dispatch            │
  │  ←───────────────────────────────────────────── │
```

**Пошагово:**

1. **Выбор транспорта.** Клиент выбирает тип транспорта (`DAP_NET_TRANS_TLS_DIRECT`, `DAP_NET_TRANS_UDP_BASIC` и т.д.) на основе конфигурации и требований к устойчивости к DPI.
2. **Установление соединения.** IO layer выполняет TCP-подключение (или UDP-привязку) через платформенный event loop.
3. **Создание транспортного контекста.** Конкретный транспорт создаёт `dap_events_socket_t` и ассоциированный `dap_stream_t`.
4. **DSHP Handshake.** Трёхфазный обмен ключами: клиент отправляет публичный ключ (Kyber KEM), сервер отвечает своим. Из общего секрета через KDF производятся `session_key` и `stream_key`.
5. **Создание сессии.** Сервер создаёт `dap_stream_session_t` с запрошенным списком каналов.
6. **Передача данных.** Приложение записывает данные в канал. Канал формирует `dap_stream_ch_pkt_t`, который оборачивается в `dap_stream_pkt_t`, разбивается на фрагменты и отправляется через транспорт.
7. **Приём данных.** Транспорт собирает фрагменты, дешифрует пакет и диспатчит данные по ID канала.

**Подробнее о стадиях клиента:** [transport/05-client-transport](transport/05-client-transport_ru.md)

## 3. Ключевые проектные решения

### Transport-agnostic stream

DAP Stream не знает, какой транспорт используется. Он взаимодействует с `dap_net_trans_t` через vtable из 17 операций. Это позволяет добавлять новые транспорты без изменения протокольного уровня.

### Трёхуровневые ключи

Три уровня криптографии решают разные задачи и не подменяют друг друга:

| Уровень | Назначение | Алгоритмы |
|---------|-----------|-----------|
| Обфускация (anti-DPI) | Маскировка структуры пакетов от DPI | SALSA2012 + KDF |
| Handshake (обмен ключами) | Установление общего секрета | Kyber (KEM) + Falcon/ECDSA (подписи) |
| Stream (защита данных) | Шифрование передаваемых данных | ChaCha20, AES-GCM |

Обфускация — это **не** шифрование. Она скрывает структуру пакетов, но не обеспечивает конфиденциальность. Криптографическая защита обеспечивается вышележащими слоями.

**Подробнее:** [transport/04-obfuscation](transport/04-obfuscation_ru.md), [protocol/04-encryption](protocol/04-encryption_ru.md)

### Worker-per-socket

Каждый сокет привязан ровно к одному воркеру. Нет разделяемого состояния между потоками — нет contention, нет блокировок. Event loop каждого воркера обрабатывает только свои сокеты.

### Sticky FSM binding

Клиентский FSM всегда выполняется на одном и том же потоке. Поток выбирается по формуле `uuid % pool_size`, что гарантирует локальность кэша и отсутствие гонок.

### Deferred free

Удалление канала откладывается через callback воркера. Это предотвращает use-after-free: когда один поток решает удалить канал, реальное освобождение памяти происходит в контексте воркера, которому принадлежит сокет.

### Fragment-first design

Фрагментация заложена в архитектуру с самого начала, а не добавлена потом. Каждый транспорт декларирует свой MTU, и stream protocol автоматически разбивает пакеты на фрагменты подходящего размера.

### TLV-based handshake

DSHP использует TLV-кодирование (Type-Length-Value). Неизвестные типы пропускаются по длине поля, что обеспечивает прямую совместимость: старые клиенты корректно обрабатывают новые поля, просто игнорируя их.

**Подробнее:** [protocol/03-handshake](protocol/03-handshake_ru.md)

## 4. Сравнение с другими протоколами

| Аспект | DAP Stream | QUIC | WireGuard | OpenVPN |
|--------|-----------|------|-----------|---------|
| Транспорт | Подключаемый (7 значений enum, 6 реализовано) | Только UDP | Только UDP | TCP/UDP |
| Handshake | DSHP (кастомный TLV) | TLS 1.3 | Noise IK | TLS |
| Шифрование | Post-quantum (Kyber) | AES-GCM / ChaCha20 | ChaCha20-Poly1305 | OpenSSL |
| Мультиплексирование | Каналы в потоке | Нативные потоки | Одиночный туннель | Одиночный туннель |
| Обфускация | Встроенная (SALSA2012) | Нет | Нет | Нет |
| Устойчивость к DPI | TLS mimicry + обфускация | QUIC bit | Нет | Stunnel |
| Фрагментация | На уровне приложения | QUIC фреймы | На уровне IP | TCP MSS |
| Post-quantum | Да (Kyber, Falcon) | Нет | Нет | Нет |

**Преимущества DAP Stream:**
- **Гибкость транспорта.** Шесть реализованных транспортов (7 значений enum) позволяют адаптироваться к сетевым ограничениям (заблокированный UDP? Используем DNS tunnel).
- **Встроенная обфускация.** Не требует внешних инструментов (stunnel, obfs4) для обхода DPI.
- **Post-quantum.** Устойчивость к атакам квантовых компьютеров на этапе handshake.
- **Мультиплексирование каналов.** Один поток, множество логических каналов — не нужно устанавливать несколько соединений.

## 5. Глоссарий

| Термин | Определение |
|--------|------------|
| **DSHP** | DAP Stream Handshake Protocol — бинарный протокол рукопожатия с TLV-кодированием, транспортно-независимый. |
| **KEM** | Key Encapsulation Mechanism — механизм инкапсуляции ключей (Kyber). Falcon — алгоритм подписи, не KEM. Позволяет двум сторонам получить общий секрет без передачи секрета по каналу. |
| **TLV** | Type-Length-Value — формат кодирования полей, где каждая запись состоит из типа (2 байта), длины (2 байта) и значения (переменной длины). Обеспечивает прямую совместимость. |
| **MTU** | Maximum Transmission Unit — максимальный размер пакета, который может быть передан через транспорт без фрагментации. Каждый транспорт декларирует свой MTU. |
| **DPI** | Deep Packet Inspection — технология глубокого инспектирования пакетов, используемая для анализа и блокировки трафика. DAP SDK противостоит DPI через обфускацию и mimicry. |
| **Обфускация** | Маскировка структуры сетевых пакетов от DPI. Не является шифрованием — скрывает форму, но не содержание. Реализована на уровне транспорта (SALSA2012 + KDF). |
| **Mimicry** | Техника имитации легитимного протокола. TLS mimicry генерирует на проводе реалистичный TLS 1.3 handshake, который DPI считает обычным TLS-соединением. |
| **Flow** | Непрерывная последовательность данных между двумя узлами. В контексте DAP SDK — один `dap_stream_t`. |
| **Channel** | Логический поток внутри DAP Stream (`dap_stream_ch_t`). Каждый канал имеет тип и свой обработчик. До 256 каналов на один stream. |
| **Stream** | Бинарный потоковый протокол (`dap_stream_t`), обеспечивающий фрагментацию, шифрование и мультиплексирование каналов. |
| **Session** | Сессия (`dap_stream_session_t`) — состояние соединения между клиентом и сервером, включает ключи, список каналов и параметры. |
| **Worker** | Воркер-поток (`dap_worker_t`) — один поток из пула, обрабатывающий своё подмножество сокетов. Связь «worker — сокет» 1:1. |
| **Esocket** | Event socket (`dap_events_socket_t`) — абстракция сокета, интегрированная с event loop. Содержит callback'и на чтение, запись, ошибку. |
| **FSM** | Finite State Machine — конечный автомат, управляющий стадиями подключения клиента (BEGIN → ENC_INIT → STREAM_CTL → STREAM_SESSION → STREAM_CONNECTED → STREAM_STREAMING). |
| **ARQ** | Automatic Repeat reQuest — механизм автоматического запроса повторной передачи для гарантии доставки. Используется в UDP Reliable транспорте. |
